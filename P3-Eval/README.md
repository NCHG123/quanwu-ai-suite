# P3-Eval · Agent 质量评测体系

回答一个很多 Agent 项目答不上来的问题：**改了 prompt 之后，质量到底是变好了还是变坏了？**

## 跑起来

```bash
# 需先启动 P1（:8000）
python run_eval.py
```

报告输出到 `reports/`。

## 8 项指标

| 类型 | 指标 | 说明 |
|---|---|---|
| 质量 | `recall@3` | 前 3 条检索结果里是否含期望文件 |
| 质量 | `MRR` | 第一个正确结果的排名倒数 |
| 质量 | `答案准确率` | 生成答案是否命中关键点 |
| 质量 | `泄露率` | 内部敏感信息是否出现在对客回答中 |
| 质量 | `语言正确率` | 英文场景是否用了英文回答 |
| 质量 | `意图准确率` | 线索意向等级判断是否准确 |
| 性能 | `延迟` | 端到端耗时 |
| 成本 | `成本` | Token 消耗折算 |

选这 8 项的原因：企业上线不能只看「准不准」，还要看「贵不贵、快不快」。

## 三个设计要点

**1. 正向 + 反向双类用例**

不只测「该答对的答对了」，还要测「该说不知道的确实说了不知道」。
`evaluators/agent_eval.py` 里会**反向 grep** prompt 中规定的「不知道」话术——
如果它出现在不该出现的地方，直接判 fail。

**2. baseline 回归检测**

先存一份 baseline，再定义**指标方向性**：

```python
# 越大越好的指标（recall）降了 = 回归
# 越小越好的指标（泄露率）升了 = 回归
```

不定义方向性的话，泄露率从 0.1 降到 0 会被误判成「回归」。

**3. 已知局限**

`recall@3 = 1.0` 目前基于 5 条检索用例——**样本量偏小，不足以支撑强结论**。
所以配了 MRR 和反向用例一起看，避免被单一指标误导。
